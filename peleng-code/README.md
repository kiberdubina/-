# Трекинг 3D

Мультикамерное обнаружение и сопровождение движущейся цели с координатами XYZ в метрах в общей системе координат. Проект хакатона (БГТУ, «Пеленг»).

Камеры — Android-телефоны или видеофайлы. Обработка идёт на ноутбуке (Windows): программа находит движущееся пятно на каждой камере, ведёт его по кадрам, триангулирует точку по двум и более камерам и показывает след, скорость и прогноз в поле 3D.

## Быстрый старт

Нужен Python 3.10+.

```bash
cd peleng-code
python -m venv .venv
.venv\Scripts\activate          # Windows; на macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python start.pyw
```

Откроется окно «Трекинг 3D». Без телефона выберите **Файл → Демо** (синтетический круг) или **Файл → Демо 3D** (две виртуальные камеры, сразу видны метры).

Для телефона по USB нужен `adb` в `PATH` (или в `%LOCALAPPDATA%\peleng-build\platform-tools\adb.exe`) и включённая отладка по USB на телефоне. Программа сама ищет подключённые телефоны каждые 2–3 с.

## Как это работает

Каждый тик окна (~33 мс) выполняется один шаг конвейера:

```
кадр → детектор пятен → 2D-трек → триангуляция → 3D-трек (Калман) → экран
```

| Шаг | Модуль | Что делает |
|---|---|---|
| Источник | `app/source.py`, `app/phone_usb.py`, `app/rig.py`, `app/way1_sources.py` | Кадр с меткой времени и `camera_id`: демо, видеофайл, URL MJPEG, телефон по USB, синтетический стенд, ролики Way1 |
| Детектор | `app/motion.py` | Пятна цели: вычитание фона MOG2, цвет HSV, цвет + движение, `ego` (крутящаяся камера), `sky_dark`, `white_blob`. Отсев по площади `s_min..s_max` |
| 2D-трек | `app/track2d.py` | Калман по пикселям, ворота к прогнозу; `MultiTrack2D` держит до 8 треков, чужое пятно не перехватывает главный |
| Связка камер | `app/session.py`, `app/geom.py` | Триангуляция по камерам с измерением и известной позой (кадры не дальше 0,08 с друг от друга), отсев по репроекции и дальности |
| 3D-трек | `app/track3d.py` | Калман 6D (XYZ + скорость), до 4 целей, прогноз на `predict_s`; трек засыпает после 90 пропусков |
| Экран | `app/main.py`, `app/view3d.py` | Окна камер с рамкой и следом, поле 3D с конусами камер, лучами и следом, строка статуса |

`app/pipeline.py` связывает детектор и 2D-трек одной камеры, `app/session.py` объединяет все камеры.

### Позы камер

Без поз камер метров нет: есть только пиксели на каждой камере. Позы берутся одним из способов:

- **Лист ChArUco** — меню «Калибровка»: «Сохранить лист ChArUco…» → распечатать → положить в поле зрения всех камер → «Снять кадр листа» → «Позы по листу». Начало координат — лист. Размер клетки задаётся в `config.yaml → board`.
- **Таблицы Way1** (`app/cine_table.py`) — позы кинокамер из CSV Unreal (сантиметры → метры, Z вверх). Поза cam-5 обновляется на каждом кадре.
- **Демо 3D** (`app/rig.py`) — позы известны заранее.

### Телефон по USB

`app/phone_usb.py` через `adb` загружает на телефон `phone/scrcpy-server` в режиме камеры (снимается сенсор, не экран), принимает поток H.264 через `adb forward` и декодирует его PyAV. При большой задержке разрешение снижается, при зависании поток перезапускается. Убранный через правый клик телефон не возвращается сам, пока снова не выбран «Файл → Телефон».

В `phone/` также лежит своё приложение `PelengCam.apk` (MJPEG на порту 8080), в текущем сценарии оно не используется.

## Меню

**Файл**
- *Телефон* — искать телефоны по USB.
- *Демо*, *Демо 3D* — синтетические источники.
- *Путь 5 камер* — ролики и позы Way1 (см. ниже).
- *Открыть видео…* / *Добавить видео…* — один файл / ещё одна камера.
- *URL потока…* — MJPEG, например `http://192.168.42.129:8080/video`. Только своя сеть.
- *Сохранить контроль…* — прогон до 120 шагов: `control_overlay.mp4`, `xyz.csv`, графики X/Y/Z.
- *Отчёт погрешности…* — сравнение 3D-следа с эталоном Way1, пишет `reports/metrics.txt`.

**Цель** — профиль цели (всё движение, чёрная футболка, зелёный мяч, БПЛА, своя цель; по описанию — человек в чёрной кофте, красная машина, грузовик, своя цель текстом, см. «Цель по описанию») и горизонт прогноза 0,25 / 0,5 / 1 с. Выбор профиля сохраняется в `config.yaml`.

**Калибровка** — лист ChArUco, см. выше.

По окну камеры: левый клик — показать только её, правый — добавить видео или убрать камеру. Уголок слева внизу поля 3D меняет его размер.

## Настройка: `config.yaml`

- `active` — активный профиль.
- `predict_s` — горизонт прогноза, с.
- `board` — размеры листа ChArUco.
- `patterns.<имя>` — профили цели:

| Поле | Смысл |
|---|---|
| `s_min`, `s_max` | площадь пятна на кадре, px |
| `u_min`, `u_max` | скорость пятна по кадру, px/с |
| `r_min`, `r_max` | дальность от ближайшей камеры, м |
| `v_min`, `v_max` | скорость в пространстве, м/с |
| `color` | HSV-диапазон (`h_min`, `h_max`, `s_min`, `s_max`, `v_min`, `v_max`) или `null` |
| `require_motion` | цвет учитывается только там, где есть движение |
| `moving_camera` | камера поворачивается: детектор `ego` |
| `mode` | `auto`, `color`, `ego`, `sky_dark`, `white_blob` |
| `d_m` | размер цели, м (пока не используется) |

Пороги меняют поведение без правки кода.

## Цель по описанию

Вместо «любого движущегося пятна» можно сказать, кого вести: «человек в чёрной кофте», «красная машина», «грузовик». Детектор (`app/object_detector.py`) отдаёт рамки в тот же 2D-трек; дальше всё как раньше.

Нужен необязательный пакет и файл весов:

```bash
pip install -r requirements-detect.txt
```

Веса сами не скачиваются. Положите в `peleng-code/models/` (в git не попадают):

- `yolov8n.pt` (6 МБ) — для режима `object`;
- `yolov8s-worldv2.pt` (~25 МБ) — для режима `text`.

Нет пакета или весов — в строке статуса причина, программа работает на детекторе движения.

**Режим `object`** — класс COCO (`person`, `car`, `truck`, `bus`…) и цвет внутри рамки:

```yaml
black_hoodie_person:
  mode: object
  class: person
  conf: 0.4                # минимальная уверенность модели
  region: upper            # где проверять цвет: full | upper | middle | lower
  color: {h_min: 0, h_max: 180, s_min: 0, s_max: 255, v_min: 0, v_max: 60}
  color_share: 0.35        # доля пикселей области в диапазоне цвета
```

`region`: `upper` — 15–55 % высоты рамки (торс без головы), `middle` — 30–70 %, `lower` — 55–95 %, `full` — вся рамка. Красный проходит через 0° по H, его задают списком из двух диапазонов (см. `red_car` в `config.yaml`).

**Режим `text`** — YOLO-World по фразе: `query: "person in black hoodie"` или список синонимов. Русский запрос переводится словарём (человек, машина, грузовик, автобус, мяч; чёрный, белый, красный, синий, зелёный, жёлтый; кофта, футболка, куртка). Цвет из запроса сам включает проверку цвета в рамке. В меню: «Цель → Своя цель текстом…» — профиль `text_custom`.

**Скорость.** Модель видит кадр, уменьшенный до `det_width` (640 px), и запускается раз в `det_every` кадров (3 для `object`, 5 для `text`); между запусками рамку ведёт 2D-Калман. Когда трек есть, поиск сначала в окне `roi_scale` × рамка (2,5) вокруг него на полном разрешении. Модель одна на все камеры; `cuda`, если есть, иначе CPU. На CPU (Apple M, `yolov8n`) — 30–110 мс на запуск; YOLO-World в 2–4 раза медленнее, без видеокарты его лучше показывать на 1–2 камерах.

**Что работает хорошо:** класс + цвет у крупных объектов на реальном видео — люди, машины. **Плохо:** тонкие признаки (логотип, фасон), мелкие и далёкие цели, рендеры. Готовый `yolov8n` грузовик Way1 почти не находит (рамка в 2–3 кадрах из 25 на камеру): цель мелкая, серая, это рендер. Для Way1 нужны веса, дообученные на кадрах роликов, — путь к ним в поле `model`.

Пороги `s_*`, `u_*`, `r_*`, `v_*` у таких профилей можно не задавать; площадь `s_*` считается по рамке, не по контуру.

Ролики и таблицы не хранятся в git (`.gitignore` исключает `*.mp4` и `*.csv`). Для «Путь 5 камер», контрольного прогона, отчёта погрешности и части тестов положите их в корень `peleng-code/` или в подпапки `видео/` и `execl/` (ищется в корне и в `видео/`, `video/`, `execl/`, `excel/`, `tables/`, `data/`):

```
Way1.FinalImage.CineCameraActor1.mp4 … CineCameraActor5.mp4
object_transform_CineCameraActor1.csv … CineCameraActor5.csv
object_transform_SM_AA_track.csv        # эталон цели, только для погрешности
```

Камеры 1–4 стоят, камера 5 только поворачивается. След 3D строится по кадрам из картинок; эталонная таблица на экране не рисуется и нужна только для погрешности (сравнение по номеру кадра).

## Контрольный прогон Way1: фура в 3D-ящике

```bash
python run_control.py            # или меню «Файл → Контрольный прогон Way1…»
```

Профиль `way1` содержит блок `vehicle` (габарит ящика и опорная точка 3D-модели фуры). С ним 3D считается не триангуляцией центра пятна, а подгонкой 3D-ящика к рамкам силуэтов во всех камерах: модель движения автомобиля (CTRV с уклоном), итерационный EKF с робастными весами, сглаживание RTS и итерации до сходимости. Фон каждой камеры — медиана по записи (поворотной cam-5 — в панораме направлений по её позе).

Результат — `reports/way1_control/`: `control_cam-N.mp4` и `control_all.mp4` (каркас 3D-ящика на каждой камере), `trajectory.csv` (XYZ опорной точки, центр ящика, курс, тангаж, скорость, эталон и ошибка по кадрам), `boxes2d.csv` (рамки силуэтов и проекции ящика), `xyz_t.png`, `plan_xy.png`, `error_t.png`, `metrics.txt`, `metrics_by_segment.csv`. Сейчас на Way1: 3D на 100 % кадров, RMSE 2,9 м, медиана 1,5 м (подробно — `docs/защита.md`). Прогон около 4 минут, камеры считаются параллельно в процессах.

В окне («Путь 5 камер») тот же профиль работает вживую: онлайн-фон, ящик в кадрах камер и в поле 3D, без сглаживания по всей записи.

## Тесты

```bash
python -m unittest discover tests
```

Тесты Way1 (`test_way1_*`, `test_cine_table`, `test_metrics3d` и др.) и `check_trail.py` требуют локальных роликов и CSV — без них они падают. Тесты на роликах мяча и дрона без своих файлов пропускаются с причиной. Новые модули (`vehicle`, `vehicle_fusion`, `background`) проверяются на синтетике с известной истиной и данных не требуют.

Служебные скрипты в корне: `check_trail.py` (след мяча без выбросов), `_eval_hold_trail.py` (удержание рамки на роликах, отчёт в `_eval_hold_trail_report.json`), `_probe_geom.py` (проверка геометрии ChArUco).

## Ограничения

- Телефоны аппаратно не синхронизированы; кадры метятся временем ноутбука. Для быстрых бросков точность падает.
- Режим точки: XYZ есть, только когда цель одновременно видят минимум две камеры с известными позами. Режим машины держит цель и одной камерой (дальность по размеру ящика и модели движения), но точность там падает до ~4–5 м.
- Камеры во время прогона не двигаются (кроме cam-5 в Way1, чья поза известна по кадру; она может только вращаться).
- Код ориентирован на Windows (`CAP_DSHOW`, запуск `adb` без окна), тесты и контрольный прогон работают и на macOS.
